# rusts3 0.9.1

A maintenance release of the upgrade tooling, from upgrading a real
installation (0.5.0 → 0.9.0: 24 buckets, 3,983 objects, metadata on NFS).
The server is unchanged apart from its version; `rusts3-migrate` is 0.1.1.
If you are on 0.9.0 already, there is nothing to do.

## rusts3-migrate 0.1.1

- **`status` works while the server runs.** It only inspects the data
  directory (no lock), and says whether a running server holds it — so you
  can see what will be converted before taking any downtime. `migrate` and
  `rollback` still require the server stopped.
- **Ownership is preserved, so running as root is safe.** Everything the tool
  creates — the new databases, a lock file it had to create — and everything
  it touches — RocksDB writes housekeeping files (log, manifest, options)
  into a database it opens, including the originals — is given the data
  directory's owner, whatever the outcome of the run. Before, a run as root
  left root-owned files that a server running as the data's user could not
  open: in the new databases, and inside the RocksDB originals (so even a
  refused or failed run could break the old server). A user who is neither
  root nor the owner is refused before anything is committed.
- **No panic when output is cut short** (`rusts3-migrate status … | head`).
- **Clearer rollback bounds**: `rollback` produces data for 0.8.x. Coming from
  0.3 – 0.7, returning to that release means restoring the
  `*.rocksdb.migrated` copies (or a backup) with the old binary — which loses
  writes made since — or going forward to 0.8 instead. Now said in `--help`,
  the README and here.

## Upgrade experience, measured

On a processmaster-managed install with its data on NFSv4.2:

| Step | Time |
|---|---|
| `rusts3 validate` of the existing 0.5.0 config with the 0.9 binary | accepted, no changes |
| Stop | 1.1 s |
| `rusts3-migrate migrate` — 28 databases, every row verified | 3.6 s |
| Swap the binary, start, healthy | 0.4 s |
| Optional tar backup of the 1.4 GB RocksDB metadata (the originals are kept anyway) | 213 s |

Everything the server served before — 24 buckets, 3,983 objects (key, ETag,
size, time), every version, IAM users, groups, keys and policies — was
identical afterwards; writes worked (PUT 12–17 ms with `durability: full`
on NFS).
