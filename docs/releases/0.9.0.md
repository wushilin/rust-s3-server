# rusts3 0.9.0

**The server no longer contains any C or C++ code.** Its metadata databases
move from RocksDB to [redb](https://github.com/cberner/redb), its outgoing TLS
from `ring` to [graviola](https://github.com/ctz/graviola), and its raw system
calls from `libc` to [rustix](https://github.com/bytecodealliance/rustix).
Upgrading needs a one-time conversion of the metadata databases with the new
`rusts3-migrate` tool — **the server refuses to start until it has run**.

Also new: a token-protected bucket directory for DNS servers and certificate
issuers, group commit for durable writes, and a fix for duplicated webhook
deliveries after a rewind.

## Security: why no C

rusts3 is a network service that parses untrusted input (HTTP, SigV4, XML,
multipart bodies) and its own on-disk metadata. Memory-safety bugs —
out-of-bounds reads and writes, use-after-free — are the class of defect
behind most remote-code-execution vulnerabilities in such software, and C and
C++ cannot rule them out; every C dependency is a place a future 0-day can
come from, however well maintained. Rust rules them out outside `unsafe`
blocks, which are small, rare, and auditable.

What was compiled into the 0.8 server, and what replaced it:

| 0.8 (C/C++) | Role | 0.9 (Rust) |
|---|---|---|
| **RocksDB** (~400k lines of C++) + `lz4-sys` (C), plus `libstdc++` at run time | Every metadata database: bucket indexes and changelogs, IAM, key usage, scans, stats, subscriptions, replication links | **redb** 3.1, pure Rust, behind a small `storage::kv` layer |
| **ring** (C and assembly) | TLS for webhook deliveries and replication connections | **graviola** 0.4 via `rustls-graviola`: Rust, with formally verified assembly from [s2n-bignum](https://github.com/awslabs/s2n-bignum) for the big-number and elliptic-curve arithmetic. No C compiler involved. |
| `libc` raw calls (3 `unsafe` blocks) | uid lookup, `openat` for GETs | **rustix** safe wrappers — 3 fewer `unsafe` blocks in this crate |

What remains, and why it is acceptable:

- **The system C library** (glibc, or musl in the static builds) — every Rust
  program uses it through the standard library; there is no practical
  alternative.
- **graviola's assembly** — the formally verified routines above; the rest of
  graviola is Rust.
- **`unsafe` inside Rust dependencies** (tokio, hyper, redb, …) — far smaller
  and easier to audit than a C codebase, but not zero: "no C" is not "no
  memory-safety bugs possible".

`cargo tree` confirms that no crate in the shipped server's dependency graph
invokes a C compiler. The only program in the repository that still links
RocksDB is the separate, offline migration tool.

The `rs3` client is unchanged in this respect (it keeps `aws-lc` through the
AWS SDK): it is a command-line tool, not a network-facing service.

### Other security-relevant changes

- **Fail-closed upgrades.** The server will not start on unconverted RocksDB
  data, naming the databases — rather than coming up with an empty IAM, or
  rebuilding a bucket index from the blobs (which would silently discard its
  changelog). A bucket whose index is still RocksDB is refused even if it
  appears later.
- **Format markers.** Every database records its format (`rusts3_format`:
  format number, the build that created it, the build that last opened it).
  A server refuses a database whose format is newer than it understands,
  instead of misreading it.
- **The changelog never publishes what a crash could take back.** Webhooks,
  pull subscribers and replication peers only see changelog entries that are
  durable. Before, under `durability: relaxed`, a consumer could receive an
  entry that a crash then lost — and the sequence number would be reused for a
  different change, which the consumer would then skip.
- **Graceful refusal instead of a crash on old CPUs.** graviola needs AES and
  carry-less multiply instructions (x86_64: AES-NI, PCLMULQDQ, AVX2, BMI1,
  ADX — roughly 2013 onward; aarch64: AES, PMULL, SHA2, NEON). On a CPU
  without them, `https://` webhook and peer URLs are refused with a clear
  message instead of panicking mid-handshake; `http://` keeps working.
- **Bucket directory tokens** (below) carry no rights at all, are compared in
  constant time, must be at least 16 characters, and every refusal is logged
  with the client address.

## Upgrading from 0.8

1. **Stop the server.** The tool takes the server's `.rusts3.lock` and
   refuses to run against a live data directory.
2. **Get `rusts3-migrate`**: it is in every server release archive and in the
   container image — with the server's container stopped:
   `docker run --rm --entrypoint rusts3-migrate -v rusts3-data:/data
   ghcr.io/wushilin/rusts3:0.9.0 migrate /data`. To build it: `cd migrate && cargo build
   --release` — it links RocksDB, so it needs a C++ compiler and libclang (the
   server itself no longer does).
3. **Check, then convert:**
   ```bash
   rusts3-migrate status  /var/lib/rusts3      # your server.base_dir
   rusts3-migrate migrate /var/lib/rusts3
   ```
   Every database is copied row for row, compared with the original, and only
   then renamed into place. The originals stay as `*.rocksdb.migrated`;
   delete them when you are satisfied. Needs free space for a second copy of
   the metadata (not of the object data). Interrupted? Run it again.
4. **Start 0.9.**

**Version bounds**, checked for every database before anything is converted:
`migrate` reads data from any RocksDB release, **0.3.0 – 0.8.x**; data from an
unknown build is refused.

**Rolling back** to 0.8: stop the server and run `rusts3-migrate rollback`. It
converts the *current* data, including everything written under 0.9, and
produces data for **0.8.x** only. It is refused once a later version has
changed the format (format marker above 1).

**Replication across versions works**: a 0.8 site and a 0.9 site replicate
each other in both directions (tested, see below), so sites can be upgraded
one at a time.

## Behaviour changes

- **`durability: relaxed`** now makes index writes durable in the background
  within about a second. A crash — including a plain process crash — can lose
  that last second of acknowledged writes. (With RocksDB, only a power loss
  could.) `durability: full`, the default, is unchanged: an acknowledged write
  survives power loss.
- **Changelog visibility** follows durability (see Security). Readers trigger
  the needed fsync themselves for writes that do not wait for one. A write
  that does wait (`durability: full`) is visible to S3 reads as soon as it
  commits, but its changelog entry appears only when its fsync completes — at
  most one group fsync later (milliseconds; longer on slow disks). Changelog
  consumers long-poll, so they simply receive it then.
- **`rs3` 0.6.0**, released alongside: `rs3 watch` verifies certificates
  against the operating system's certificate store instead of a bundled list
  (reqwest 0.13).
- **Database files**: `<base_dir>/admin.redb`, `key_usage.redb`,
  `scans.redb`, `stats.redb`, and `buckets/<bucket>/index.redb` — single files
  instead of directories.

## New: bucket directory

For infrastructure that only needs to know which buckets exist — a DNS server
answering `<bucket>.<public_hostname>`, a certificate issuer or admission
hook validating a name:

```bash
curl -H 'x-list-bucket-token: <token>' http://s3.example.com:8002/_rs3/buckets
# {"buckets":[{"name":"photos","created_at_ms":1763800000000}, …]}
curl -I -H 'x-list-bucket-token: <token>' http://s3.example.com:8002/_rs3/buckets/photos
# 200 if it exists, 404 if not
```

Configure `auth.bucket_list_tokens` (container: `RUSTS3_BUCKET_LIST_TOKEN`).
With no token configured, the endpoint does not exist. A token cannot sign S3
requests or read anything beyond bucket names and creation times.

## Durability and performance

redb allows one writer per database and has no built-in group commit, so a
naive port would pay one fsync per write. 0.9 adds **group commit**: each
write commits without an fsync and gets a generation number; one committer
fsyncs on behalf of everything committed so far, advances the durable
generation and wakes every waiter it covered — event driven, no polling.
Writes already on their way join the group before the fsync starts.

Measured on the development VM (btrfs, virtual disk, ~12 ms per fsync):

| | 0.8 (RocksDB) | 0.9 (redb) |
|---|---|---|
| One durable commit | 11.9 ms | 13.1 ms |
| 128 durable writes from 16 threads | — | 8–9 fsyncs |
| Two-way replication stress test (4 writers, rebuild, restart) | 82.6 s / 85.0 s | 79.3 s / 79.5 s |
| Clean build of the server | RocksDB alone: 11–27 min | ~1 min |

Read performance was the reason redb was chosen over other pure-Rust
engines: redb's own published benchmarks show point lookups and range scans
about 3× faster than RocksDB. **That has not yet been measured through
rusts3's own storage layer**, which adds overhead of its own; a benchmark is
pending.

## Fixes

- **Webhook replay delivered twice.** A rewind (`SetOffset`) landing while
  the delivery worker was between reading its generation and its state made
  it deliver the replayed range, discard its own progress as stale, and
  deliver the range again. Generation and state are now read together under
  the lock that rewinds change them under.

## Compatibility

- **Replication**: 0.8 ↔ 0.9 in both directions, mirror and merge, plain and
  versioned buckets — tested with real 0.8.0 and 0.9 sites (over `http://`).
- **Data**: converts data written by 0.3.0 – 0.8.x; rolls back to 0.8.x.
- **APIs**: S3, console and changelog APIs are unchanged; the bucket
  directory is additive.

## Dependencies

- New: `redb` 3.1, `rustls` 0.23 (no default provider) with
  `rustls-graviola` 0.4 / `graviola` 0.4, `webpki-roots` 1, `rustix` 1.
- Removed from the server: `rocksdb` / `librocksdb-sys` / `lz4-sys`,
  `ring`, `libc` (direct use).
- `reqwest` 0.12 → 0.13 (server and client), plus every compatible update.

## How this release was tested

- Server: 625 unit and integration tests, AWS golden replay, AWS SDK
  compatibility — all pass. Client: 164 unit tests and 20 end-to-end suites
  pass. Migration tool: 8 tests (round trip, idempotence, interrupted commit,
  conflicting copies left alone, lock held by a server, failed copy, version
  bounds both ways).
- **Real-data round trips**: the actual 0.7.0 and 0.8.0 binaries created
  buckets, versions, delete markers, a multipart object, tags, users, groups,
  keys and subscriptions; `rusts3-migrate` converted them; 0.9 served exactly
  the same (listings, version histories, object bodies by hash, IAM,
  subscription positions, object counters); 0.9 wrote more; `rollback`; the
  old binary served everything, the new writes included. Identical in both
  directions, for both versions.
- **Mixed-version replication**: a 0.8.0 site and a 0.9 site with merge
  links owned by each side converged to identical contents, version histories
  and version ids.
- A live TLS handshake through graviola.

## Known limitations

- Read performance through rusts3's storage layer is not yet benchmarked
  against 0.8.
- Replication between 0.8 and 0.9 over `https://` peers was not tested (both
  speak standard TLS 1.2/1.3).
